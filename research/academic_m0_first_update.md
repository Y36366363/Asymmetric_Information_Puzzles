## 新的证据索引

`research/claim_evidence_index.json` 目前记录六类主张：通用 sequence-form、
固定策略计算、五骰候选、分层观测、Love Letter 边界，以及尚未确立的通用
LLM 求解目标。每条都有规则范围、局限、证据路径、文件哈希和下一问题。
部分主张还检查 JSON 内的具体状态，避免只引用文件名就声称通过。

运行 `python scripts/audit_research_claims.py` 可检查引用是否一致。
脚本成功不代表每项实验成功；五骰整体失败也是必须追溯的有效结果。
哈希只记录版本一致性。知道规则的人仍然需要审查主张是否真的由证据支持。
代码源文件哈希发生变化时，需要重新审查该引用，并在同一提交说明理由；
不应为了让 CI 变绿自动刷新所有哈希。

## 本次必须理解的三个科研概念

1. **回归测试与重复实验不同。** 检查 JSON 的历史数字能发现结果被误改，
   但不会重新执行训练或模型 API。测试套件也有现场重新求解的小型游戏，
   应按具体测试区分。再次独立训练、再次调用模型才产生新的实验观测。
2. **模型内正确与规则语义正确不同。** 想象骗子骰子 adapter 把对手骰子
   放进自己的 information-set key。求解器可能对这个错误游戏算得完全正确。
   检查“换一个看不见的对手骰子，自己的信息集应不变”才能抓住这种泄露。
3. **研究假设与工程里程碑不同。** CI 和证据索引让结果可靠、易复查，
   本身不足以构成 AAMAS 方法创新。真正待检验的贡献是：语义检查能否发现
   普通结构审计漏掉的错误，并帮助 LLM 在未见规则上修复建模。

## AIP 拟争取的特色

已有平台和自动形式化工作是必须比较的基线。本项目下一步聚焦游戏的
“谁知道什么”：私有状态泄露、同时行动的信息屏蔽、对手 policy 未声明导致
posterior 不可识别等错误，并让诊断输出绑定具体规则、反例和修复义务。
这一方向是待验证的差异化假设，不能提前声称首创。

GameSpec 初期需要明确玩家、chance、公开轨迹、私有观测、合法行动、收益和
终止规则。评估用的语义合同应来自可信规则 reference，与 LLM 生成模型分开。
一骰和 Goofspiel 已有可靠参考，可先检验它们的信息边界。

## 下一次由你理解后再推进的最小实验

先对一骰构造一个“泄露对手骰子”的故障 adapter，以及一个正确 adapter。
测通用结构审计与独立观察不变性合同分别能否识别故障；同时保留正确模型的
通过结果。若结构审计已经能抓住该故障，就据实调整错误分类，而非预设结果。
初次只检验一个故障类别，之后扩展到 Goofspiel 的同时行动泄露。

你可以先用自己的话回答：为什么对一个泄露私骰的模型算出 exploitability=0，
仍不足以说明真实游戏已求解？以及“观察不变性”应比较哪些状态、允许哪些信息
变化？这两点理解清楚后，再决定 GameSpec 的字段与实验细节。

本次尚未启动 GameSpec、故障 adapter 或新的 LLM 实验；这些属于下一步。
完整 M0 还需要干净环境复现与更完整的环境记录，本次不把它标记为全部完成。
